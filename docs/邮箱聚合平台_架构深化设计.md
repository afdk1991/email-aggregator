## A. 模块接口与时序设计

### A.1 统一连接器接口（Canonical Connector）

所有第三方邮箱以**适配器插件**实现同一接口，框架按 `providerType` 路由；适配层负责协议↔统一邮件模型的双向映射。

```typescript
// 连接器元信息
type ProviderType = "imap" | "pop3" | "exchange" | "gmail" | "enterprise";

interface ConnectorCapabilities {
  incremental: boolean;        // 是否支持增量（IMAP QRESYNC / Graph delta / Gmail historyId）
  push: boolean;               // 是否支持服务端推送（IMAP IDLE / Webhook）
  folders: boolean;            // 是否支持多文件夹（POP3=false）
  flags: boolean;              // 是否支持旗帜/已读（POP3=false）
  maxPageSize: number;
}

interface Connector {
  readonly providerType: ProviderType;
  readonly capabilities: ConnectorCapabilities;

  // 建立连接（凭据经 KMS 解密后仅存于短期内存）
  connect(account: AccountCredential): Promise<Session>;

  // 列出文件夹（POP3 返回单一 INBOX 语义视图）
  listFolders(session: Session): Promise<Folder[]>;

  // 增量拉取：以 watermark 为游标，返回新/变更邮件 UID 列表
  fetchChanges(session: Session, folder: string, cursor: SyncCursor): Promise<ChangeSet>;

  // 按 UID 拉取完整邮件（含 MIME）
  fetchMessage(session: Session, folder: string, uid: string): Promise<RawMessage>;

  // 订阅推送（IMAP IDLE / Graph Webhook）；不支持则抛 NotImplemented
  subscribe(session: Session, folder: string, hook: PushHook): Promise<Subscription>;

  // 发送（SMTP 或 Graph sendMail / Gmail send）
  send(account: AccountCredential, message: OutboundMessage): Promise<SendResult>;

  healthCheck(session: Session): Promise<Health>;
}
```

**统一邮件模型（Canonical Mail Model）**——内部唯一表示，屏蔽协议差异：

```typescript
interface CanonicalMail {
  idempotencyKey: string;      // (accountId, folder, messageId) 幂等去重键
  accountId: string;
  folder: string;              // 统一文件夹名（INBOX/SENT/DRAFTS/TRASH/JUNK/自定义）
  messageId: string;           // RFC822 Message-ID
  from: Contact[]; to: Contact[]; cc: Contact[];
  subject: string;
  bodyText?: string; bodyHtml?: string;
  attachments: Attachment[];   // contentHash 用于去重
  flags: { seen: boolean; flagged: boolean; answered: boolean; deleted: boolean };
  internalDate: number;        // 收件时间戳（ms）
  sizeBytes: number;
  // 协议侧游标（仅适配层关心，不进入检索模型）
  cursor: SyncCursor;
}

interface SyncCursor {
  uidValidity?: string;        // IMAP
  uidNext?: string;            // IMAP
  highestModSeq?: string;      // IMAP CONDSTORE/QRESYNC
  historyId?: string;          // Gmail
  deltaLink?: string;          // Graph
  uidlWatermark?: string;      // POP3
}
```

### A.2 同步编排状态机

每个账户维护一个同步状态机，由 `sync-orchestrator` 驱动；错误进入退避，成功回到守护态。

| 状态 | 含义 | 进入条件 | 退出动作 |
|------|------|----------|----------|
| `UNCONNECTED` | 未连接/未授权 | 新建账户 | 触发 OAuth 授权 |
| `AUTHORIZING` | 授权中 | 拿到授权码 | 换取并 KMS 加密 token |
| `INITIAL_FULL` | 初始全量回溯 | 首次/重新全量 | 分批 fetch + 限速，写 `sync-tasks` |
| `INCREMENTAL` | 增量守护 | 全量完成 | IDLE/轮询 + `fetchChanges` |
| `THROTTLED` | 被限流/退避 | 429/节流 | 指数退避后回 `INCREMENTAL` |
| `ERROR` | 错误态 | 连续失败超阈值 | 告警 + 人工/自动复核 |
| `PAUSED` | 用户暂停 | 用户操作 | 恢复后回 `INCREMENTAL` |

事件：`AUTH_OK / FULL_DONE / CHANGE_RECEIVED / THROTTLED / TRANSIENT_ERR / FATAL_ERR / RESUME`。

### A.3 Kafka 事件契约

所有事件带 `partitionKey = accountId`（保证单账户有序、可再均衡），`idempotencyKey` 用于消费端去重。

| 主题 | 生产者 | 消费者 | 关键字段 | 语义 |
|------|--------|--------|----------|------|
| `sync-tasks` | orchestrator | ingestion | accountId, folder, cursor, priority | 至少一次 |
| `mail-ingested` | ingestion | store / index / notify / audit | canonicalMail, source | 至少一次 + 幂等 |
| `mail-index` | index-service | search-engine | docId, accountId, bodyText | 异步建索引 |
| `notifications` | notify | ws-push / webhook | accountId, kind, preview | 至少一次 |
| `audit` | 各服务 | 审计存储 | actor, action, accountId, ts | 至少一次 |

`mail-ingested` 示例 payload：

```json
{
  "partitionKey": "acc_8f21",
  "idempotencyKey": "acc_8f21|INBOX|<msgId>",
  "canonicalMail": { "subject": "...", "from": [...], "internalDate": 1765738800000 },
  "source": "imap", "ts": 1765738801000
}
```

### A.4 关键时序：新邮件增量同步（IMAP IDLE）

详见对话内「新邮件同步时序图」：

1. Connector 对 IMAP 服务器发起 `IDLE`（长连接推送）。
2. 服务端有新邮件 → 下发 `EXISTS` 通知。
3. Connector 用 `fetchChanges(cursor)` 拉取新增 UID（基于 `highestModSeq`）。
4. 取回完整 MIME → 归一化为 `CanonicalMail` → 产出 `mail-ingested`。
5. `mail-ingested` 落 PG 元数据（按 `accountId` 分片）+ 内容写入对象存储（内容寻址）。
6. 索引服务消费 → 写 OpenSearch（按 `accountId` 路由）。
7. 通知服务推送 WebSocket/SSE 给客户端；审计写 `audit`。
8. 更新游标（`highestModSeq`）到账户状态，保证断点续传。

### A.5 关键时序：多协议初始全量回溯

`INITIAL_FULL` 态分批回溯：按文件夹分页 `fetchMessage`，每批带限速令牌；遇上游 429 进入 `THROTTLED` 退避；完成后切 `INCREMENTAL`。POP3 以 `UIDL` 集合做全量去重（无增量游标）。

## B. 容量规划计算模型

### B.1 参数表（可调）

| 参数 | 符号 | 默认 | 说明 |
|------|------|------|------|
| 连接账户数 | `A` | 1,000,000 | 可聚合多邮箱/人 |
| 单账户日均新邮件 | `M` | 50 | 封/天 |
| 单封元数据大小 | `sMeta` | 2 KB | 发件人/主题/时间/文件夹等 |
| 单封内容+附件 | `sBody` | 75 KB | 含附件均值 |
| 索引膨胀系数 | `kIdx` | 2.0 | 索引/元数据 |
| 留存期 | `Y` | 2 | 年 |
| 活跃比 | `ρ` | 0.3 | 当日活跃账户比例（影响计算/连接） |

### B.2 公式

```
元数据总量   = A × M × sMeta × 365 × Y
内容总量     = A × M × sBody × 365 × Y
索引总量     = 元数据总量 × kIdx
日均采集事件 = A × M
峰值采集吞吐 = 日均采集事件 / 86400 × 峰值系数(≈8)   // 事件/秒
并发 IMAP 长连接 = A × ρ × 长连接占比(≈0.6)
检索 QPS     = A × 人均日检索(5) / 86400 × 峰值系数
年度存储增量 = 元数据 + 内容 + 索引（按年）
```

### B.3 场景测算

| 指标 | 10 万账户 | 100 万账户 | 500 万账户 |
|------|-----------|------------|------------|
| 元数据总量 | 7.3 TB | 73 TB | 365 TB |
| 内容总量 | 0.27 PB | 2.7 PB | 13.5 PB |
| 索引总量 | 15–22 TB | 150–220 TB | 730–1,100 TB |
| 日均采集事件 | 500 万 | 5,000 万 | 2.5 亿 |
| 峰值采集吞吐 | ~460 evt/s | ~4,600 evt/s | ~23,000 evt/s |
| 并发 IMAP 长连接 | ~1.8 万 | ~18 万 | ~90 万 |
| 峰值检索 QPS | ~460 | ~4,600 | ~23,000 |
| 年度存储增量 | ~0.3 PB | ~3 PB | ~15 PB |

> 数字为模型估算，上线后须以真实遥测（实际 `M`、附件占比、留存策略）校准；交互计算器见对话内「容量规划计算器」。

### B.4 扩展杠杆与成本

- **冷热分层**：热 30 天存标准对象存储，冷转低频/归档层（成本可降 60–80%）。
- **索引分级**：仅正文 / 含附件名 / 全量 OCR 三档，按付费套餐控制。
- **内容寻址去重**：相同附件（如群发邮件）只存一份，降低存储放大。
- **计算弹性**：采集 worker 按 `kafka lag` 扩缩，闲时缩容省成本。

## C. Phase 0 PoC 落地计划

### C.1 目标与范围（MVP）

验证**单协议（IMAP）端到端闭环**：单邮箱账户授权 → 增量同步 → 落库/落对象存储 → 检索 → Web 阅读。不做多协议、不做企业版、不做 HA。

### C.2 技术选型

| 项 | 选型（PoC 建议） | 说明 |
|----|------------------|------|
| 语言 | Go 或 Java 21 | 并发友好，适配长连接 |
| 元数据 | PostgreSQL（单实例） | 后续按 `accountId` 分片 |
| 内容 | 本地 MinIO（S3 兼容） | 后续换托管对象存储 |
| 索引 | OpenSearch 单节点 | 后续集群化 |
| MQ | 本地 Kafka（或 Redpanda） | 验证事件契约 |
| 前端 | React SPA + WebSocket | 阅读/检索 |
| 编排 | docker-compose | 不做 K8s |

### C.3 任务拆解（含估算，单位：人天）

| # | 任务 | 依赖 | 估算 |
|---|------|------|------|
| T1 | IMAP 连接器（IDLE + QRESYNC + 归一化） | — | 8 |
| T2 | 账户/凭据管理（OAuth2 + KMS 占位） | — | 5 |
| T3 | 同步编排状态机 + `sync-tasks` | T1 | 6 |
| T4 | 采集/解析服务（MIME → CanonicalMail） | T1 | 6 |
| T5 | 存储写入（PG 元数据 + MinIO 内容） | T1 | 5 |
| T6 | 索引服务 + OpenSearch 检索 API | T5 | 6 |
| T7 | 通知（WebSocket 推送） | T4 | 3 |
| T8 | BFF/API 网关 + 前端阅读/检索 | T5,T6 | 10 |
| T9 | 可观测性埋点（同步成功率/时延） | — | 4 |
| T10 | 联调 + 验收演练 | 全部 | 5 |

**合计 ≈ 58 人天（约 2.5 个月 / 1 个 3 人小队）。**

### C.4 验收标准（退出 Phase 0）

- [ ] 单 IMAP 账户可授权接入，新邮件 ≤60s 在 Web 可见（IDLE）。
- [ ] 断点续传：重启后从 `highestModSeq` 继续，无重复入库（幂等键校验）。
- [ ] 检索 P95 < 500ms（单用户收件箱级）。
- [ ] 内容/附件可从对象存储还原，正文可全文检索。

## D. HA/DR 与备份深化

### D.1 Patroni 高可用（PostgreSQL）

- 3 节点 etcd/Consul 存放领导者信息；Patroni 管理主从，自动故障转移。
- 同步复制模式（`synchronous_commit = on`）保护元数据不丢；副本跨 AZ。
- 故障转移 < 30s；应用通过 VIP / 服务发现连当前主库，连接串自动切换。
- 连接池 `PgBouncer` 前置，避免长连接打爆主库。

### D.2 跨可用区 / 跨区域复制

| 组件 | AZ 内 | 跨 AZ | 跨区域（DR） |
|------|-------|-------|--------------|
| PostgreSQL | 主从 | 副本（同步） | 异步流复制（关键租户） |
| Kafka | 多 broker | 副本 ≥3 | MirrorMaker2 异步 |
| OpenSearch | 多节点 | 分片副本 | 快照跨区 |
| 对象存储 | 多副本 | 跨 AZ | 跨区复制（合规租户） |
| Redis | 集群 | 副本 | 不跨区（可重建） |

### D.3 备份与 PITR

- 元数据：每日全量 + WAL 连续归档 → 对象存储；`recovery_target_time` 支持 PITR（RPO ≤ 5min）。
- 内容：对象存储版本化 + 生命周期归档；无需传统备份。
- 索引：ILM 快照，可重建（ rebuilt from 元数据+内容，代价高但非必须）。
- 密钥：KMS 密钥材料随备份**受控复制**到异地密钥库（与数据备份配对）。

概念性恢复流程：

```
# 1) 拉起基线
pg_basebackup -D /restore ...
# 2) 回放 WAL 到目标时间
recovery_target_time = '2026-08-14 22:00:00+08'
# 3) 校验一致性后开放只读，再切主
```

### D.4 混沌演练与 RPO/RTO 验证

- 季度级故障注入：杀主库 / 断 AZ 网络 / 灌爆 Kafka / 模拟上游 429。
- 验证项：自动故障转移时效、RPO（对比 WAL 位点）、RTO（服务恢复时长）。
- 上游故障演练：断开 IMAP 服务器，确认平台进入**降级模式**且阅读体验不中断。

### D.5 降级模式实现要点

- 读路径优先命中本地已聚合数据（PG 元数据 + 对象存储内容 + OpenSearch 索引）。
- 写/同步路径入队（Kafka）排队重试，前端显示"同步中/稍后重试"。
- 上游限流 429 → `THROTTLED` 指数退避，不占用平台资源。
- 单适配器熔断：某服务商异常不影响其他服务商与其他用户。
